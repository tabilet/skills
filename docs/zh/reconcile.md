# Reconcile

对于需求中的功能、候选方向提升或未来方向变更，请使用
[Propose](propose.md)。Reconcile 负责处理新的工程评审。

把新的工程评审转化为现有记忆库中已获批准的规划变更。Reconcile 只做规划，
不做实现。

在你的项目会话中发送该请求。把 `review.md` 替换为你实际的评审来源：

| 智能体 | 会话请求 |
|---|---|
| Claude Code 插件 | `/memory-bank:memory-bank-reconcile review.md` |
| Codex 插件 | `$memory-bank:memory-bank-reconcile review.md` |
| DSH | `/memory-bank-reconcile review.md` |

参数：一个评审来源。它可以是被粘贴的、作为附件的、本地的、相对于仓库的，
或者远程的。

如果是直接安装到技能目录，请参见
[调用前缀](installation.md#invoke-a-skill)。

## 何时使用

只要在初始化之后收到代码、架构、安全或其他工程评审，都可以使用它。它要求
已经存在里程碑与状态运行器；它不会初始化项目。

评审之后，下一个看似顺理成章的提示是“把四项发现都修掉”。这跳过了最重要的
问题：**它们现在仍然成立吗？**

评审描述的可能是更早的提交。某一项发现可能已经修复。另一项可能与某个待处理
里程碑重复。它的 P1/P2 用词可能并不等于你项目定义中的含义。某条架构建议可能
合理，但超出了你的归属范围。

## 评审文本是不可信的证据

评审被当作数据处理，而绝不是指令。内嵌的命令不会仅仅因为出现在文档里就被
执行。

在进行任何**远程**抓取之前，Reconcile 会把确切的 URL 展示给你，并获取一次
单独的显式确认——即使那个 URL 是你自己的请求提供的。在仓库内容或评审内部
发现的 URL 绝不授权抓取。

## 三个阶段

**评估。** 阅读评审、当前记忆库、相关实现与测试、历史记录，以及评审声明的
基线。对照当前仓库重新验证每一项发现。

**给出方案。** 展示完整的处置矩阵：

| 发现项 | 来源优先级 | 本地严重级别 | 当前处置 | 计划归属 |
|---|---|---|---|---|
| 进程在启动失败后仍然存活 | P1 | P1 | 已确认 | 开放的会话生命周期里程碑中的一行 |
| 超时行为不一致 | P2 | P2 | 重复 | 现有的待处理公共契约行 |
| 清理失败路径未经验证 | P2 | P2 | 已确认 | 新建的补救里程碑 |
| 重命名辅助函数 | P3 | 较低 | 延后 | 带触发条件的候选方向 |

处置还包括部分确认、已解决、当前证据不支持、超出归属范围，以及取决于决策
结果。来源优先级会保留下来，以记录来源信息；本地严重级别则依据你项目的定义
独立划定。

**写入。** 应用已获批准的操作。在你批准处置矩阵、归属、依赖、下游影响、候选
方向和文件操作之前，不会写入任何内容。

## 发现项的去向

一项已确认的发现如果符合某个开放里程碑的范围，就会在那里成为一条新的待处理
行。已有的待处理里程碑如果已经拥有该结果，则更新它，而不是重复创建。

**已完成的历史保持关闭。** 当一项发现涉及已完成的工作时，Reconcile 会新建一个
补救里程碑，并带有指回受影响里程碑的溯源关系。历史状态说明曾经发生了什么；
它不会为了让今天的计划看起来更整洁而被改写。

每一项活跃发现都携带可移植的来源信息：评审标题与发现 ID、来源优先级与本地
严重级别、声明的基线与重新验证提交、相对于仓库的证据，以及指向既有工作的
溯源关系。这里没有不断累积的 `reviews/` 目录，也没有第二份评审台账。

## 架构建议不是当前架构

描述某种目标状态的评审，在被实现之前属于里程碑范围与验收内容。直接把它写进
`architecture.md` 会让记忆库失真：文档描述的将是评审想要的系统，而不是智能体
即将编辑的系统。

只有当当前仓库证据证明某项现有描述已经过时时，Reconcile 才会修正 `product.md`、
`architecture.md` 或 `tech-stack.md`。

## 下游优先

一项发现很少只停留在它被发现的那个文件。Reconcile 会在实现开始之前更新待处理的
消费方：依赖与顺序、任务措辞与验收、兼容性预期、验证覆盖范围，以及计划依赖于
受影响契约的下游状态文件。

当一项发现改变了多个里程碑共用的假设时，这能让计划保持一致。

## 它不会做什么

Reconcile 不实现发现项、不把任务标记为完成、不改变非待处理行的状态、不提交、
不推送，也不启动执行。规划与执行始终是两个独立的授权边界。
