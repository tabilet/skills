# Upgrade

## 将 v1.5.0 项目迁移到 v2 {#migrate-a-v150-project-to-v2}

v2 把 `AGENTS.md` 留在项目根目录，Memory Bank 文件则移到 `tabilet/` 下，包括
`GOAL.md`、`memory-bank/`、`evolution/`、归档和已退役的历史。其他项目文档仍留在根目录。
安装 v2 绝不会移动这些文件；v2 技能和 API 运行器一碰到旧版布局或混合布局就停下。
v2 的 DSH 侧边栏能以只读方式显示 v1.5.0 项目，并给出迁移警告。

用 Upgrade 技能随附的标准库命令，或者 v2 源码检出里的同一个文件。起点是已提交、
干净的 Git 工作区：

```bash
python3 /path/to/skills/skills/memory-bank-upgrade/migrate-v1.5-to-v2.py /path/to/project
python3 /path/to/skills/skills/memory-bank-upgrade/migrate-v1.5-to-v2.py /path/to/project --apply
```

第一条命令只预览文件操作。`--apply` 才真正移动文件、更新需要维护的说明和索引，同时
逐字节保留冻结归档和退役记录，最后把差异留着不提交，方便评审。其他项目文档里的路径
引用它也会列出来，交给你人工核对。全部退役的项目、只做归档的预检、缺失或自定义的
goal 协议，以及本地策略，它一样支持。对于那些没改动过的 v1.5.0 `GOAL.md`，它会把唯一
那处路径示例更新成 v2 的位置。自定义过的 `GOAL.md` 则逐字节保持原样，而且每次都会被
标出来，要求人工核对路径。

中途被打断，就用 `--resume` 跑同一条命令。继续之前，它会检查三样东西：受跟踪项目文件
之外的临时日志、Git `HEAD`，以及每个计划处理的文件哈希。遇到说不清的部分布局、符号
链接或目标冲突，它会停下来等人工修复。全部完成之后，再跑一次不会产生任何改动。

评审完差异和项目检查之后，按你项目的常规策略提交。工作流规则如果也要更新，就用下面
的 Upgrade，那是另一次独立的获批合并。

## 升级工作流规则 {#upgrade-workflow-rules}

通过获批的合并升级现有记忆库的工作流规则，同时保留项目计划、本地策略和历史。

在你自己项目的会话里发送这个请求：

| 智能体 | 对话请求 |
|---|---|
| Claude Code 插件 | `/memory-bank:memory-bank-upgrade` |
| Codex 插件 | `$memory-bank:memory-bank-upgrade` |
| DSH | `/memory-bank-upgrade` |

可选参数：你想采用的工作流变更。

技能文件夹如果是直接安装的，请参见[调用前缀](installation.md#invoke-a-skill)。

## 何时使用它

装完新技能之后，你想让现有项目采用新的工作流规则，就用这个技能。

项目必须已经有一套里程碑/状态文件，已经全部退役但索引历史仍然有效的项目也算。应用获批的升级之前，先暂停同一账本上正在进行的其他执行。

光装上更新后的技能，没法安全地重写每一个用过旧版本的项目。这些项目有自己的命令、
策略、计划和历史。**安装永远不会迁移项目。** 采用靠的是这个技能，而且必须你点头才会
动手。

## 三个阶段

**先检查对照。** Upgrade 会把项目已经采用的工作流，跟技能里随附的参考模板逐项对比。
有了这个包，检查目标既不用检出，也不用联网。它会找出缺失的规则、可以沿用的本地写法、
有意排除的项，以及需要你拍板的冲突。

**再提方案等批准。** 它给出具体的文件操作，是聚焦到章节的差异，而不是把整份文档重述
一遍，然后就等你批准。

**最后应用并验证。** 批准之后它应用作用域内的合并，再验证保留是否真的生效。

## 一个有用的请求

```text
Use memory-bank-upgrade to compare this project's workflow with the bundled
contract. Preserve our plans, local policies, task states, IDs, review counts,
and history. Show the complete proposed file changes before writing.
```

## 哪些内容会保留

任务状态、永久标识符、本地策略、评审计数器、自定义 goal 协议、已完成的证据，以及冻结
历史。已经兼容的项目一处都不用改。

## 升级不是什么

升级采用的是一套**运行规则**。它不会顺手帮你初始化项目、实现工作、提交或退役里程碑。

退役旧里程碑是另一件独立的工作，需要自己的作用域，也需要自己的关闭证据。单独安装的 API 运行器，
也要自己再做一次兼容性检查或更新。

## 采用长期记忆

项目如果已经积累了好几个月的历史，这个技能就是最要紧的一个，因为 `lessons.md` 和里程碑
退役正是靠它，才进得去一个比它们更早的项目。

现有项目得显式采用这两样能力。不存在自动的批量迁移，退役也遵守每一种提交策略。

## 如果 DSH 报告兼容性警告

就算仪表盘读不全记录，你照样可以准备 Upgrade 请求。**Insert into empty draft** 只是准备好
文本；真正发送出去，才是让智能体检查并提出变更。它并不代表你批准了合并。

把警告一并放进对话：侧边栏是把警告和请求文本分开显示的。在提修正方案之前，先让智能体
分清哪些是不受支持的旧语法、哪些才是真正的账本冲突。ID、状态、备注、评审证据和历史都
要保留，不要为了消掉警告就批量重写它们。
